\section{4. Architecture}

\subsection{4.1 Context diagram (C4 Level 1)}

The context view fixes the boundary. Everything the system knows about the building
comes through BuildSim's REST API, and everything it does to the building goes back
the same way. The operator uses a browser. The occupants are simulated inside the
system and are shown here as the people the system is for, because their presence
is what the safety interlocks protect. There is no external compute: the proposal's
overnight model training would have been the one candidate, and it was not needed.

\subsection{4.2 Container diagram (C4 Level 2)}

The container view opens the box. There are four separately running parts, and only
one of them is this project's code.

\begin{figure}[H]
\centering
\includegraphics[width=0.90\linewidth]{images/container.png}
\caption{C4 Container diagram (Level 2). The dashed boundary is the system; the two grey containers are BuildSim's. Every arrow carries its protocol.}
\label{fig:container}
\end{figure}

\textbf{Why one service.} The proposal's nine containers would each have held one
of the four zones. I did not build it that way, for one
reason: simulated time. The whole point of the system is to run a fire at
forty times real time and still have a 25-second dwell mean 25 simulated seconds.
Across a broker, every message would need a simulated timestamp, every subscriber
would need to wait for every publisher before advancing, and a slow dashboard
consumer could stall the physics. Inside one process the tick loop advances the
world, samples the sensors, thinks and acts in a fixed order under one lock, and
``now'' is one number. The price is that the zones share a process, so a crash in
one takes the others with it. Section~13 says what that costs and what would change
if the system left the laptop.

\textbf{What keeps the zones apart}, since process boundaries do not, is the
package layering: \code{domain} (pure, standard library only, no clock, no network),
\code{adapters} (everything that speaks HTTP to BuildSim), \code{app} (the tick loop,
the API and the snapshot). The dependency arrow only points inward, and a test,
\code{test\_layering}, fails the build if any module imports the wrong way or if
anything in the intelligence path touches the true room state.

\textbf{The control panel} is a separate container because it has a different
lifecycle: it is built once with Vite into static files, served by the service, and
talks to it only through the REST endpoints and the server-sent event stream, the
same interface a script would use. It has no knowledge of the engine's internals.

\subsection{4.3 Component diagram (C4 Level 3): inside the firelab service}

The service is the one container complex enough to need its own picture. Its
components are the four zones of one tick, plus the three things that sit around
them. The three groups are the truth boundary: the components in the orange group
may read the real state of the rooms, the components in the two blue groups may
not, and the only thing that leaves the orange group is a sensor reading.

\section{5. Interfaces and communication}

Three patterns are used, each where it fits. \textbf{REST} carries every command
and every call to BuildSim, because each is a one-to-one request whose result the
caller must know: a refused command comes back with the interlock's reason.
\textbf{Server-sent events} carry the snapshot to the control panel, because that is
one-way, high-rate and needs no reply. \textbf{WebSocket} is BuildSim's own channel
to its viewer and is used, not built. There is no pub/sub, for the reason given in
Section~4.2.

\textbf{Naming.} A room is addressed everywhere as \code{level/name}, for instance
\code{level2/A3505}, because a bare name is not unique across storeys. A device is
\code{fl-<level>-<room>-<modality>}, so its room and kind can be read off its ID.
Units are fixed and never carried in messages: temperature in °C, smoke as optical
obscuration in 1/m, CO in ppm, distances on the plan in half-metre units, and
simulated time in seconds since midnight.

\textbf{The control-panel API.} Every request body is a typed model; unknown keys
are rejected by the framework before the engine sees them.

\textbf{The snapshot} is the one data structure the panel reads. Each monitored
room appears as below, and the three columns of the Rooms table are the three
objects in it: what is true, what was reported, and what the system believes.

\begin{verbatim}
{"key": "level2/A3505", "level": "level2", "name": "A3505", "kind": "room",
 "truth":   {"temperature": 648.0, "smoke": 0.668, "co": 107.0},
 "reading": {"temperature": 250.0, "smoke": 0.665, "co": 101.0},
 "p_fire": 0.994, "state": "CONFIRMED", "tenable": false,
 "sprinkler": true, "door": "closed", "occupants": 0,
 "devices": [{"id": "fl-level2-A3505-smoke", "modality": "smoke",
              "fault": "none", "reading": 0.665}, ...]}
\end{verbatim}

The temperature reading of 250 against a truth of 648 is not a bug in the example.
It is the heat detector's range clamp, and it is the kind of thing the snapshot
exists to make visible.
